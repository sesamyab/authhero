# Week 43 · 19 – 25 October 2026

Pagination is the theme. **The `include_totals` envelope changes** to match
Auth0 — `length` is now the size of the page and `total` the overall count —
which fixes admin tables that could not get past their first page, and will
matter to any client of yours that read `length` as the total. Cursor
pagination reached nearly every remaining list endpoint. SAML grew up as an
identity provider: its flow is logged, and single logout exists. Password
reset now requires a single-use credential tied to the session that asked for
it. Management API logs finally say who made a change, not just who it was
made to. And the groundwork for tenant configuration inheritance landed, with
migrations but no change in behaviour yet.

## List responses: `length` and `total`

**If you read `length` from a list response, check your code.** With
`include_totals=true`, the management API sent the overall match count as
`length` and, for most lists — `/users` among them — no `total` at all. Auth0
sends `length` as the number of items on the returned page and `total` as the
overall count. AuthHero now does the same, on every list.

The visible symptom was in the admin UI, where the users table read
"1–10 of 10" and offered no further pages; all pages are reachable again. The
tenants list reports `total` too.

Cursor pagination — `from` and `take`, answered with an opaque `next` — now
covers:

- a user's sessions, logs, organizations, permissions, roles and connected
  applications;
- an organization's invitations, enabled connections and member roles;
- hooks, actions, forms, flows and grants;
- dead-lettered events.

On these endpoints it is an AuthHero extension; Auth0 pages them by offset
only, and offset paging is unchanged. A shared conformance suite now runs
against the kysely, drizzle and DynamoDB adapters, checking that a walk visits
every row exactly once even when rows are inserted or deleted between pages,
and the DynamoDB adapter gained the methods it was missing. An endpoint whose
adapter cannot page by cursor answers 501.

Two bugs fell out of the work: on drizzle, listing a role's permissions
ignored `page` and `per_page` and returned everything; on kysely, the name of
the API a permission belongs to was resolved through the wrong column.

## SAML: a log trail, and single logout

When AuthHero acts as the SAML identity provider, a failed login at the
service provider used to leave nothing in the tenant logs. The whole flow is
logged now: the request arriving at `/samlp/{client_id}`, every way it can be
rejected, and the assertion being issued — with the application, the NameID
and where it came from, audience, destination and signing key. The assertion
itself is never logged.

Log entries across a login also carry `details.login_session_id`, so the
`/authorize` request, the login screens and the final successful-login entry
can be tied together as one flow.

Single logout is implemented at `/samlp/{client_id}/logout`, for both
bindings. The metadata had been advertising that endpoint without it
existing. It revokes the session named by the request's `SessionIndex`,
triggers back-channel logout, logs the outcome, and answers with a
`LogoutResponse` to the application's configured logout callback. Two limits
for now: logout request signatures are not verified — an application that
requires signed requests is refused — and the response is not signed.

## Password reset is bound to its session

A password reset is now modelled as a workflow owned by the login session
that started it. Changing a password requires an active reset request, a
credential — the emailed code or link — that matches it, is unexpired and has
not been used, and a submission by the same method the request used. A new
request supersedes earlier credentials, and the request, not the mutable
login parameters, decides whose password is being reset. Emailed reset links
keep working through validation errors and through both the form and JSON
submission paths.

After a successful reset on `/u2`, the user lands on the password step with a
"password reset" confirmation. Before, a tenant with both emailed-code and
password logins could send someone who had just set a new password to a
screen asking for an emailed code.

## Management API logs record the caller

For an operation such as "Update a User", the log's `user_id` names the user
who was changed — as in Auth0 — and until now nothing named who did it. Logs
of management API calls now carry Auth0's `details.request.auth`:

```json
"auth": {
  "user": { "user_id": "email|admin", "name": "Admin", "email": "admin@example.com" },
  "strategy": "jwt",
  "credentials": { "jti": "…", "scopes": ["update:users"] }
}
```

A person's token fills in `auth.user`; a client-credentials token has no
user, and the log's `client_id` is taken from the token.

**Two things move.** The caller's token scopes are no longer copied into the
log's top-level `scope`; they are under `auth.credentials.scopes`. And log
streams now send the same `user_id` as the logs table — the affected user,
where streams used to send the caller. If a consumer of your log stream
treated `user_id` as the actor, read `details.request.auth` instead.

## Tenant configuration inheritance: the schema

The first two steps of a larger change landed: letting a tenant inherit
connections, actions, hooks, APIs, branding and email settings from a parent
tenant, with rules for what a child may override. This week is schema and
measurement only.

- **Migrations to apply.** Tenants gain `parent_tenant_id`; connections,
  actions, hooks, resource servers, branding, prompt settings and email
  providers gain `scope`, `override` and `enforce`. Every column is nullable
  and an unset value reads as today's behaviour. Nothing reads them yet.
- **A shadow mode**, off by default. With `inheritanceShadow` enabled on
  `initMultiTenant`, reads start a background comparison between today's
  result and what inheritance would produce, and log differences as `cfgdiff`
  entries you can query per tenant. The comparison is never used to serve a
  request.

## Also

- **Login screens** — prompt partials render on the login screens as well as
  signup (`login-id`, `login-password` and `login`), enough to add a terms
  link under the form, and the admin UI's Partials tab offers them. Custom
  fields on login are not processed yet.
- **Social login** — a user who had edited their email could no longer sign in
  with the provider they registered with; the lookup was by email and
  provider, missed, and the attempt to create them failed with "User already
  exists". Users are now found by the provider's own subject first.
- **Account linking** — linking a primary account onto one of its own
  secondaries used to fail the login with a 400. It now promotes the
  secondary instead.
- **Sessions** — exchanging a refresh token no longer extends the expiry of
  the login session it came from. Nothing resolves through that record any
  more.
- **Tenants** — the tenant search matches the tenant's ID as well as its
  display name, so searching for a slug finds it.
- **Admin UI** — "Manage tenants" in the tenant switcher no longer leads to
  Not Found, and an application's Login link moved from the list to a button
  on its detail page.
- **Docs** — a new page of log-stream recipes for Datadog and Splunk,
  including the relay a Splunk HEC endpoint needs, and a note that stream
  types other than `http` are accepted but not delivered. The repository has
  a security policy with a private reporting link.
