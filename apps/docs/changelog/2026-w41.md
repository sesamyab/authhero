# Week 41 · 5 – 11 October 2026

If you use `@authhero/multi-tenancy`, read the first section before anything
else: two of its guarantees — per-tenant database isolation and the protection
of entities synced from the control plane — turned out never to have taken
effect, and both are fixed this week. Everyone else gets a password login that
no longer tells a caller whether an account exists, by error code or by
timing; if a client of yours matches on the old error codes, it needs a
change. Logins through a social or enterprise provider now keep the standard
profile claims the provider sends, so the `address` and `profile` scopes
return something, and the signup logs line up with Auth0's.

## Multi-tenancy: two guards that never ran

**Database isolation.** `databaseIsolation.getAdapters` lets each tenant live
in its own database. The middleware that installs the tenant's adapter did
run — and then every AuthHero route group replaced it with a stack built from
the adapter given at startup. The auth API, universal login, SAML, SCIM and
the management API therefore read and wrote the **shared** database, not the
tenant's. It has been this way since the package was introduced. A setup
using subdomain routing with `databaseIsolation` was affected; on Workers the
middleware also wrote to the `env` object shared between requests, so a
concurrent request for another tenant could be pointed at the wrong database.

The route groups now build their per-request stack on whatever adapter an
earlier middleware installed. **Upgrade `authhero` and
`@authhero/multi-tenancy` together** — isolation takes effect only with both.
Note that `getAdapters` replaces both the data adapter and the management
data adapter for the request, and that once this takes effect a tenant's
traffic goes to its own database: if that database was never populated
because traffic was landing in the shared one, check where the data is before
you roll out. The database-isolation page in the docs now covers mount order
and what was broken.

**Protection of synced entities.** `initMultiTenant` registered the guard
that stops a child tenant modifying roles and connections synced from the
control plane — but registered it after the management routes were already
mounted, so it never ran. Child-tenant administrators could change or delete
synced roles and connections. Resource servers were not affected; they have
their own check.

`init()` gains a `managementApiMiddleware` option — middleware that runs
inside the management API after authentication and tenant resolution, before
any route — and `initMultiTenant` now installs the guard through it. **After
upgrading, those requests answer 403**, as documented and intended. If you
wired multi-tenancy up by hand with
`app.use("/api/v2/*", createProtectSyncedMiddleware())`, that line never ran
either; move it:

```ts
init({ managementApiMiddleware: [createProtectSyncedMiddleware()] });
```

It is worth checking whether any synced role or connection in a child tenant
was changed or deleted while the guard was inactive.

## Password logins no longer reveal whether an account exists

A failed password login used to answer differently depending on why it
failed: an unknown email got `USER_NOT_FOUND`, a wrong password got
`INVALID_PASSWORD`. `/co/authenticate` passes the error through to the client
as it is, so anyone could test whether an address had an account. The timing
gave the same answer — the unknown-user path returned before any password
hashing was done.

All three failure cases — unknown email, wrong password, a linked account
that cannot be resolved — now answer identically: `403`, code
`INVALID_CREDENTIALS`, message "Wrong email or password." The unknown-user
path does the same hashing work as a real comparison, so response time no
longer distinguishes them. And the lockout is checked after the password
comparison: wrong guesses against a locked account get the same response as
any other wrong guess, and only a login with the correct password is told
`TOO_MANY_FAILED_LOGINS`.

**If a client matches on `USER_NOT_FOUND`, `INVALID_PASSWORD` or the old
messages, it will see the new code instead.** Tenant logs still distinguish
the cases — `fu` for an unknown user, `fp` for a wrong password — because
those are for you, not the caller.

## Provider profile claims reach the user

When someone signs in through a social or enterprise connection, only a fixed
list of fields was copied from the provider's profile onto the user: names,
picture, email verification and phone. The other standard claims were stored
with the provider's raw profile and nowhere else — while the `address` and
`profile` scopes read only from the user. A Vipps user who had granted their
address had it stored, and `scope=openid address` returned nothing.

`address`, `birthdate`, `locale`, `zoneinfo`, `middle_name`, `gender`,
`website` and `profile` are now copied onto the user too, following the
connection's `set_user_root_attributes` setting like the existing fields. A
value that would not fit its column is skipped rather than truncated. Vipps
phone numbers are stored in E.164 form, with the leading `+`.

## Signup logs match Auth0

A signup with enforced email verification used to be logged as a
verification request, a **failed login**, a verification, then a successful
login — so every such signup counted as a failed login, and the signup itself
was missing. Signups through the `/u2` signup screen, the classic `/u/signup`
page and invitation acceptance now log `ss` (successful signup), as
`/dbconnections/signup` always did. A login that continues into the
verification step no longer logs a failure, and the verification log carries
the connection and strategy. If you count `f` events to measure failed
logins, expect the number to drop.

## Also

- **Login page** — text typed into the `/u2` fields before the page finished
  loading used to be wiped, leaving the submit button disabled; a password
  manager's autofill or a fast typist on a slow connection would hit it. The
  widget now keeps it. For end-to-end tests there is a `data-ready` attribute
  on `<authhero-widget>`, set once the widget is interactive and removed
  while a submit is in flight — wait on `authhero-widget[data-ready]` rather
  than on a timeout. Back links across the password, code and verification
  screens read "Back to login" in every language, where some read "Back" and
  two read "Back to login Continue".
- **Logout** — a logout whose return URL is not in the application's Allowed
  Logout URLs now shows a branded page explaining that the user is still
  signed in, and naming the rejected host so a support screenshot says which
  domain to add. It used to be a white page reading "Invalid redirect uri".
  Still a 400, and still no redirect.
- **Impersonation** — the `/u2` impersonation screen matches the classic one:
  a Continue button for carrying on as yourself, and a separate box for
  impersonating someone else, which now moves the session to that user and
  records who did it on the log entry.
- **Management API** — `GET /api/v2/roles/{id}/permissions` supports
  checkpoint pagination with `from` and `take`. On the DynamoDB adapter, a
  checkpoint walk over connections no longer stops after the first page.
- **Docs** — the token-exchange standards page and the Auth0 comparison
  describe Custom Token Exchange, replacing a note that said foreign subject
  tokens were out of scope.
