# Week 40 · 28 September – 4 October 2026

A dense week. Signing keys can now carry certificates issued from a CA you
control, so an API verifying tokens from many tenants can trust one root
instead of keeping a list of issuers. `/authorize` reads signed request
objects the way the specification requires, which closes a way to smuggle
unsigned parameters into a signed request — and changes how such requests are
answered. A user with an unverified email now lands on a verification step
that finishes the same login, instead of an error under the password field.
For operators there is a switch for how much action console output is stored,
a way to discard dead-lettered events, and a dry run for kysely migrations.
And three management endpoints that answered "success" for an ID that does
not exist now answer 404.

## Signing certificates from your own CA

Until now every signing key carried a self-signed certificate, so an API
accepting tokens from many tenants — each with its own issuer, possibly on a
custom domain — had to keep a registry of which issuer belongs to which
tenant and keep it in step with your domains. Pass
`signingCertificateAuthority` to `init()` and new and renewed signing
certificates are issued from your intermediate CA instead.

Each certificate names its owner in a URI: `urn:authhero:tenant:<id>` for a
tenant's key, `urn:authhero:control-plane` for a shared one. The JWKS
publishes the chain (`x5c`) and thumbprint (`x5t#S256`) for those keys, so a
resource server pins one root and reads the tenant off the certificate.

- **Where the CA key lives is up to you.** `createLocalCertificateIssuer`
  signs in-process. `createHttpCertificateIssuer` and
  `createCertificateIssuerApp` run the CA as a separate service, so the CA key
  never has to be in the auth server; the service requires an authorization
  check and caps certificate lifetimes.
- **Renewal is a scheduled job.** CA-issued certificates default to 30 days.
  Call `renewSigningCertificates()` from a scheduled handler, the way you call
  `runRetention`, and certificates close to expiry are re-issued. The key pair
  is kept, so the `kid` and every token already issued stay valid.
- **Workers for Platforms.** `createWfpTenantApp` takes the same option, and
  the control plane can push renewal to tenant workers from its own schedule.
  A tenant worker's certificates always name the tenant, never the control
  plane.

Without the option nothing changes: existing self-signed keys stay as they
are until they rotate out, and SAML keys remain self-signed.

A related opt-in: `rejectUnknownHosts` makes `/.well-known/*` return 404 for
any host that is not the issuer host, a subdomain of an existing tenant or a
registered custom domain. Today those endpoints answer for whatever host
reaches the server. It is off by default.

## Signed authorization requests are read strictly

**This changes how some requests are answered.** When `/authorize` received a
signed request object (`request` or `request_uri`), it merged the signed
parameters over the query string — so anything the signed payload left out,
such as `scope`, `state` or `audience`, could be supplied unsigned. The
specification for signed requests says the server must use only what is
inside the object. Now it does:

- **Only signed parameters count.** The query string is read for `request` or
  `request_uri` and for the outer `client_id`, and nothing else.
- **The object must name its client.** A request object without a
  `client_id`, or with one that differs from the outer `client_id`, is
  rejected with 400.
- **A conflicting duplicate resolves to the signed value.** It used to be
  rejected; the financial-grade conformance tests expect the signed value to
  win.
- **Nothing is filled in from a stored login session** for a signed request.

If you send signed request objects, make sure every parameter you rely on is
inside the object. Requests without a request object are unaffected.

## Verifying an email during login

If an application sets `email_validation` to `"enforced"`, a user whose email
is unverified used to be stopped at the password screen with an error under
the field. A verification link had been sent, but the screen did not say so,
the link ended on a bare "Email verified." page, and the login had already
been marked failed — the user had to start again from the application.

There is now a proper step, and the connection's
`attributes.email.verification_method` chooses it:

- **`"code"`** — the default. The user is emailed a six-digit code, enters
  it, and the **same** login continues.
- **`"link"`** — the user sees a "check your email" screen, and the emailed
  link brings them back to the login screen.

Both screens can resend the email, and signup no longer sends two
verification emails when verification is enforced.

The page a verification link opens is now branded and translated, with a
Continue button back to the application: its Application Login URI if that is
HTTPS, otherwise the origin the user signed up from. Opening a link twice
shows the verified page again rather than an error, which matters for mail
scanners that prefetch links. The link only verifies the address — it never
signs anyone in, so it is safe to open on another device.

Alongside this, the `/u2` screens stopped leaking English. A handler error
used to be shown as an English banner even when the screen already showed the
translated error on the field — a Swedish signup page saying "Passwords don't
match" twice, once in each language. About eighty such strings across the
login, signup, password-reset, passkey, MFA and invitation screens now come
from the locale files, and the account, consent and connect screens are
translated into every supported language.

## For operators

- **Decide what action output is stored.** Anything an action writes to the
  console is saved with its execution record, and an action on the
  credentials-exchange trigger writes one on every token exchange. The new
  `init({ actionExecutionLogs })` takes `"full"` (the default, unchanged),
  `"errors"` (output is kept only for actions that failed or denied access)
  or `"off"`. The execution record itself is always written. Pass the same
  value to `runOutboxRelay` so actions delivered through the outbox follow it.
- **Discard dead-lettered events.** An event that will never succeed can be
  deleted instead of sitting in the dead-letter list:
  `DELETE /api/v2/failed-events/{id}` for one, or
  `POST /api/v2/failed-events/bulk-discard` for up to 100. Both need
  `update:logs` and can only ever delete an event that is already
  dead-lettered.
- **Preview kysely migrations.** `planMigrations` lists the pending
  migrations and the SQL each would run, without writing anything:

  ```ts
  import {
    planMigrations,
    formatMigrationPlan,
  } from "@authhero/kysely-adapter";
  console.log(formatMigrationPlan(await planMigrations(db)));
  ```

  A pending migration that reads a table an earlier pending migration creates
  is reported as an error in the plan, since that table does not exist yet.

- **`ctx.var.data` replaces `ctx.env.data`.** Each request's adapter stack
  now lives on the request context. `ctx.env.data` still works and points at
  the same object, but is deprecated and will be removed in a future major;
  use `ctx.var.data` in middleware, hooks and custom routes. This is the
  permanent form of last week's Workers fix — the stack belongs on the
  request, not on an object every request shares. If you build a `Variables`
  object by hand, in a test mock for example, it now needs a `data` field.

## A permission for staff who work across organizations

`access:all_organizations` is a new Management API permission. A user holding
it at global scope can get organization tokens for, and list, every
organization without being a member of each — the case of support or
head-office staff who need to open any customer's organization with the
permissions of a global role. Unlike `admin:organizations`, it needs no
tenant flag and grants no tenant-admin rights.

Every organization check — login, silent authentication, refresh and token
exchange — now applies one shared rule. A side effect: `admin:organizations`
combined with the inherit-global-permissions flag is now honoured on
`/authorize` and silent authentication too, where it was previously ignored.

## Where a login came from

A post-login action or webhook now receives the original `/authorize` URL in
`request.url`, and log streams receive it on successful-login events as
`details.request.authorization_url`. The login completes on a callback
request whose query string holds only `code` and `state`, so until now the
parameters the application started the login with — `utm_*` and the like —
were out of reach. AuthHero does not parse them; you do. The URL can contain
arbitrary query parameters and is delivered to your configured webhooks and
streams, so treat it accordingly. It is not stored in the logs table.

Two losses were fixed alongside: with the outbox enabled, the login's
`redirect_uri` and `execution_id` were dropped from logs and log streams, and
long authorization URLs were truncated at 1,024 characters in stored login
sessions.

## Also

- **Management API** — **three requests that reported success now answer
  404** on the kysely adapter: `DELETE /api/v2/sessions/{id}`,
  `POST /api/v2/sessions/{id}/revoke` and `DELETE /api/v2/refresh-tokens/{id}`
  for an unknown ID, or one belonging to another tenant. Nothing was ever
  deleted in those cases; only the status was wrong.
  `POST /api/v2/organizations/{id}/members` validates every user ID before
  adding anything, answering 400 instead of 500 for an unknown user, and
  re-adding an existing member is a no-op even when the user belongs to
  several organizations. `GET /api/v2/roles` supports checkpoint pagination
  with `from` and `take`.
- **Login page** — on laptop-height screens the `/u2` social buttons collapse
  into a row so the form stays above the fold: two buttons show icon and
  provider name, three or more show icons only.
- **Contributing** — the repository now requires Node `^22.13.0 || >=24`,
  where it used to accept Node 18 and later.
