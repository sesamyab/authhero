# Week 45 · 2 – 8 November 2026

Two things to act on. If you upgraded to `authhero` 9.28.0 and use
`tenantDispatch`, every management API request has been answering 500 —
upgrade to 9.28.3 or later. And multi-factor authentication was reworked
this week, with **two migrations that must run before the new code is
deployed**: an MFA code can no longer be guessed without limit or submitted
twice, a completed challenge is remembered on the session so the next
application does not ask again, and ID tokens say when MFA was performed.
The rest of the week is the result of someone following the Workers for
Platforms guide from an empty Cloudflare account and fixing everything that
got in the way — several published packages could not be installed or built
at all.

## Multi-factor authentication, hardened

**Run the kysely or drizzle migrations before deploying.** Two nullable
columns are added — one on sessions, one on authentication methods — and a
custom adapter must implement the new
`authenticationMethods.consumeTotpStep`.

- **Guessing is capped.** The MFA screens had no limit on wrong codes, so a
  six-digit code could be brute-forced inside one login once the first factor
  was known. After five wrong TOTP or SMS codes the login fails and later
  codes are rejected, correct ones included. With a rate limiter configured,
  each attempt also counts against the user's brute-force budget, and SMS
  sends are capped at five per login.
- **A TOTP code works once.** A code used to be accepted for its whole
  validity window, about ninety seconds, however many times it was submitted.
  The last accepted time step is now stored and a code at or before it is
  refused — on the login challenge and on both enrollment screens.
- **MFA is remembered on the session.** Completion lived only on the login
  that performed it, with two consequences. Signing in to a second
  application on the same session asked for MFA again; now it does not. And
  silent authentication (`prompt=none`) succeeded on a session that had never
  completed MFA — one from before the tenant required it, say; it now answers
  `interaction_required`. Sessions record what happened in Auth0's
  `authentication.methods[]` shape.
- **ID tokens carry `amr`.** After a completed TOTP or SMS challenge the ID
  token includes `amr: ["mfa"]`, and keeps it for the rest of the session —
  on tokens from a refresh, from silent authentication and from single
  sign-on to another application. It is absent when no MFA was performed.
- **An action can require MFA for one login.**
  `api.multifactor.enable(provider)` in a post-login action challenges the
  user after all actions have run and before tokens are issued, with any
  factor the tenant has enabled. `"none"` never switches off MFA that the
  tenant policy or another action requires.

`tenant.mfa.policy` also accepts Auth0's `all-applications` and
`confidence-score`. Adaptive MFA is not implemented, so `confidence-score`
is enforced like `always`. **One request now fails:**
`PUT /api/v2/guardian/policies` answers 400 for an unknown policy value,
where it used to accept it and silently set the policy to `never`.

## The management API behind tenant dispatch

**A regression in 9.28.0, fixed in 9.28.3.** With `tenantDispatch` set, every
management API request answered 500 with
`Cannot read properties of undefined (reading '0')`. The server build was
inlining its own copy of part of Hono, and last week's change to keep
control-plane routes out of the dispatch called into the host application's
Hono with it. Hono's subpath imports are now left external. A side benefit:
an `HTTPException` thrown by AuthHero now passes your application's own
`instanceof HTTPException` check.

Separately, `PATCH /api/v2/tenants/settings` was resetting what you did not
send. A body that omitted `deployment_type` set it back to `shared`, one that
omitted `provisioning_state` set it to `ready`, and patching a single MFA
factor switched the MFA policy and every other factor off. The patch now
applies only the keys present. **If you have patched tenant settings through
the API recently, check those fields.**

## Single sign-on in Safari

Since January the session cookie has been set only as a partitioned
cross-site cookie. Some Safari configurations do not send that cookie on a
top-level `/authorize` reached through a redirect from another site, so the
person was shown the login form on every visit although they were signed in.
The cookie is now set both partitioned and unpartitioned.

To make the next case of this diagnosable, successful-login logs carry
`details.session_cookie` — what `/authorize` received and how the session
lookup went — and `details.private_browsing`.

## Starting from an empty Cloudflare account

Following the Workers for Platforms deployment guide from
`npm create authhero@latest` to a tenant with its own database turned up a
chain of breakages, now fixed:

- **`authhero` could fail to install with npm.** It declared an optional peer
  dependency on a widget version that was never published.
- **`@authhero/admin` shipped empty.** Every published version from 0.24.1 to
  0.26.2 contained no build output, so a scaffold using `--admin-ui` could
  not build. The release now builds the admin UI, and packing fails if the
  output is missing.
- **A Cloudflare scaffold failed `npm install`** on a peer-dependency
  conflict between `wrangler` and the Workers type definitions.
- **Seeding a tenant failed on D1.** Creating the admin role bound more
  parameters in one statement than D1 allows; role permissions are now
  written in batches.
- **The admin UI could not sign in on a deployed host**: `seed()` only
  allowed localhost callbacks. Pass `issuer` and it now allows that origin's
  callback and logout URLs on the default application. An application that
  already exists is left alone, so add the URLs yourself for an existing
  tenant.

The templates now come wired for configuration sync: the control-plane
template reaches tenants that have their own worker through a dispatch
namespace binding and forwards tenant-scoped management calls to them, and
the tenant template is built on `createWfpTenantApp`. The guide itself was
corrected step by step and gained a section on running a control plane.

## Configuration sync, in practice

Fixes from running last week's sync against real tenants with their own
databases:

- **Every tenant showed as drifted.** For a tenant with its own worker, the
  applied hash was recorded only in the tenant's database, not on the control
  plane that reports status. And a control plane that encrypts at rest hashed
  decrypted values while a sync copies ciphertext, so the two never agreed.
  The hash is now recorded on the control plane, and `initMultiTenant` takes
  an optional `storedDataAdapter` — the layer that returns secrets as stored
  — for building and hashing what a sync sends.
- **A sync carries the control plane's public signing keys.** A tenant that
  was onboarded by hand, or has not seen a key rotation, can verify
  control-plane tokens after its next sync instead of needing a re-seed.
- **`PATCH /tenants/{id}`** changes a tenant's sync mode and parent on the
  control plane by ID. For a tenant with its own worker, the settings
  endpoint is answered by that worker, which rightly refuses the change; the
  admin UI now saves these two fields on the control plane.

`@authhero/cloudflare-adapter` now declares the versions of `authhero` and
`@authhero/multi-tenancy` it actually needs, so a lockfile can no longer keep
an older one beside it and fail at the first sync.

## Also

- **Admin UI** — an application's page shows only the settings and tabs that
  apply to its type, as the Auth0 dashboard does: a machine-to-machine
  application no longer shows Connections, Organizations, Refresh Tokens or
  the login-screen options. You can set the client ID when creating an
  application. A user's identities table marks the primary identity, and the
  Link user dialog explains which account becomes the primary. Saving an
  action against a server older than 9.28 works again.
