# Week 42 · 12 – 18 October 2026

The signup form became extensible this week. Prompt partials — Auth0's way of
adding your own fields and markup to a login screen — are stored, served,
rendered and editable in the admin UI, and partials exported from an Auth0
tenant work as they are. The pre-registration hook grew to match: it sees the
custom fields, can reject a signup with a message of its own, and its
metadata setter now does what Auth0's does, **which changes behaviour for
hooks that used it to set profile fields**. SAML logins had been skipping
post-login hooks altogether; that is fixed. And the drizzle adapter gained
its last three missing members, with a migration.

## Custom fields on the signup form

A prompt partial is a fragment of HTML you insert at a fixed point of a login
screen: before or after the form fields, in the footer, around the secondary
actions. The signup screen now renders them, which is how you add a field for
a company name, a terms checkbox or a marketing opt-in without replacing the
page.

- **Managing them.** `GET` and `PUT /api/v2/prompts/{prompt}/partials` are
  Auth0-compatible, so Terraform and the Deploy CLI round-trip them. In the
  admin UI, the prompts editor has a new Partials tab with a field builder —
  label, type, required, placeholder, maximum length — an HTML mode for
  fragments imported from Auth0, and a live preview of the signup screen.
- **What a partial may contain.** HTML, `<style>`, `<script>`, inline event
  handlers and Liquid are accepted and stored unchanged, as Auth0 documents.
  Markup that could escape the page or hijack the form is rejected with a 400
  naming what was found: `iframe`, `object`, `embed`, `base`, `meta`, `link`,
  a nested `form`, SVG, URLs that are not `http(s)`, `mailto` or `tel`, and
  attributes such as `formaction`. A fragment may be up to 100,000 characters.
- **Fields are submitted and kept.** Inputs whose names start with `ulp-` are
  sent with the signup, and their values survive when the screen is rendered
  again after an error.
- **Rules are enforced on the server.** `required`, `maxlength` and `pattern`
  on a `ulp-` input are checked when the signup is posted, not just hinted to
  the browser; a failure re-renders the screen with the error beside the
  field and creates no user.
- **Fields can map onto the profile.** An AuthHero extension: put
  `data-authhero-map` on an input and its value is written to `given_name`,
  `family_name`, `name`, `nickname`, `picture` or a `user_metadata` key
  before the pre-registration hooks run. The mapping is read from the stored
  partial only, so nothing the browser sends can change where a value lands.

Partials are stored per tenant by the kysely, drizzle and DynamoDB adapters
and are included in tenant export and import. **The kysely and drizzle
adapters each add a migration** for the new table. Only the signup prompt
renders partials so far.

## Pre-registration hooks see the form and can refuse it

Three changes to the `pre-user-registration` trigger, all towards Auth0:

- **The custom fields arrive.** Submitted `ulp-` fields are passed to the
  hook as `event.request.body`. Passwords, the email and unrelated form
  fields are not. A user created through the management API or a social
  login still has no request body.
- **A hook can reject with its own message.**
  `api.validation.error(code, message)` stops the signup, shows the message
  on the signup screen and keeps what the person typed. The action's
  execution is recorded as cancelled with the code and message.
- **`setUserMetadata` writes to `user_metadata`.**
  `api.user.setUserMetadata(key, value)` used to write to the root of the
  user, so `setUserMetadata("given_name", …)` set the profile field. It now
  merges into `user_metadata`, as in Auth0, and a new
  `api.user.setAppMetadata` merges into `app_metadata`. **A hook that relied
  on the old behaviour to set root attributes will now create a
  `user_metadata` key instead** — set those attributes through the user
  payload.

## SAML logins run post-login hooks

For a SAML login, the response to the service provider was built before the
step where post-login hooks run. Everything that hangs off that step was
skipped: page and form hooks, actions, webhooks, and the successful-login log
entry. If you have a post-login action that enforces a policy, it was not
running for SAML.

The hooks now run first, and the SAML response is built for the user as the
hooks left it. Impersonation works for SAML logins as a consequence, and the
`/u2` impersonation screen no longer fails with "Failed to generate redirect"
when the response is a SAML form rather than a redirect. Expect
successful-login log entries for SAML logins to appear where there were none.

## The drizzle adapter is complete

An audit of the drizzle adapter against the adapter contract found three
database-backed members missing: `organizationConnections`, `logStreams` and
`migrationSources`. They are implemented, **with a migration to apply**. With
that, drizzle covers every member that is backed by the database; the rest —
cache, rate limiting, email and SMS delivery — are supplied by the host by
design.

## Also

- **Login page** — the `/u2` login warns people who open it inside an in-app
  browser — Instagram, Facebook, a WebView — and recommends the device's own
  browser, as the classic page did; sign-in with a social provider often fails
  in those. It also warns in a private window, where the session will not
  outlive the window. Neither banner shows in the embedded login.
- **Bulk import** — a row carrying an explicit `user_id` that matched an
  existing user was mistaken for a retry of the row's own earlier write. With
  `upsert: true` the user was never updated; with `upsert: false` the row
  reported `inserted` without writing anything. It now updates under upsert
  and otherwise fails with `USER_ALREADY_EXISTS`, as Auth0 does.
- **Publishing** — the packages' repository metadata points at the repository
  they are built from, which npm's provenance check requires; a release had
  failed to publish over the mismatch.
- **Contributing** — the pre-commit hook no longer builds the workspace and
  runs every test suite; it scans for secrets, formats staged files and
  type-checks what changed. The full build and tests run in CI.
