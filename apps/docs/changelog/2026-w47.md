# Week 47 · 16 – 22 November 2026

**If you run a multi-tenant control plane, upgrade this week.** A token
scoped to one tenant's organization could act on any other tenant, and on the
control plane itself; that is closed, along with a related gap in tenant
operations. With those fixed, self-service became possible: someone can sign
up on the control plane, create a tenant of their own and administer it,
within limits you set. Session transfer tokens — Auth0's Native to Web SSO —
carry a signed-in user from one application to another, including across
top-level domains where a cookie cannot follow. MFA can remember a device.
There are **several migrations this week, and one that will fail if your data
has duplicates** — see _Migrations_ below before deploying.

## Security fixes for control planes

**An organization-scoped token is bound to its tenant.** On a control plane
an organization _is_ a tenant, and a token scoped to an organization carries
the permissions of that organization's roles. Nothing tied the token to that
tenant: by naming another tenant in the `tenant-id` header it could act
there, including on the control plane. A member of one tenant holding a role
with `update:users` or `update:roles` could change the control plane's users
and roles and make themselves an operator, and any tenant administrator could
manage other tenants' users and applications. The management API now answers
403 when such a token is used against any tenant other than the one its
organization names. Tokens without an organization, and tokens issued by a
child tenant, are not affected.

**Tenant operations are scoped to tenants the caller can reach.** Any
control-plane token with `read:tenant_operations` could read every tenant's
operations, and one with `create:tenant_operations` could start any operation
on any tenant. Operators still reach every tenant; everyone else reaches only
the tenants whose organization they belong to, and gets 404 for the rest. A
new, narrow scope, `retry:tenant_provisioning`, allows exactly one thing: an
upgrade on a reachable tenant whose provisioning failed. A resource server
seeded before this scope existed needs it added.

**A login ticket is bound to its connection.** A ticket issued by
`/co/authenticate` can now be redeemed at `/authorize` only for the
connection that verified the credentials; any other `realm` is rejected with
`403 Invalid realm`. Tickets issued before the upgrade are not redeemable —
the user signs in again.

`@authhero/multi-tenancy` now requires `authhero` 9.33.0 or later, because
the roles described below are only safe with the first two fixes. **Upgrade
the two together.**

## Carry a session between applications

Two websites on different top-level domains cannot share a session cookie, so
a user signed in to one arrives at the other as a stranger. Session transfer
tokens solve that, and are compatible with Auth0's Native to Web SSO.

The sending application exchanges its refresh token at `/oauth/token` with
`audience=urn:{domain}:session_transfer` and receives a single-use token that
lives for sixty seconds. The receiving application passes it to `/authorize`
— as the `session_transfer_token` parameter or the
`auth0_session_transfer_token` cookie, whichever it is configured to accept —
and the user is signed in without a prompt.

- **It fails soft.** A token that is reused, expired, presented from a
  different IP address, meant for another organization, or whose refresh
  token has been revoked leads to the normal login page and a warning in the
  log. It is never an error page.
- **Settings are per application**, under `session_transfer`, with Auth0's
  defaults filled in, and on a new Session Transfer tab in the admin UI,
  which warns when tokens are accepted in the URL with no device check.
- **Revocation follows the chain.** Sessions and refresh tokens created from
  a transfer remember where they came from; revoking the sender's refresh
  token ends them, unless the sender turns that off.
- **Beyond Auth0:** any application type may create tokens, a token works on
  every domain of the tenant, a transferred login can be allowed to pass the
  session on again, and a confidential application can bind the token to the
  end user's address when it is calling on their behalf.

Post-login actions see the transfer in `event.session_transfer_token` and
`event.session.session_transfer`.

## Sign up and create your own tenant

Creating a tenant has needed `create:tenants` since last week, which left a
new sign-up on a control plane with nothing to do but ask an administrator.
Four options on `initMultiTenant` make self-service work; all are off unless
you set them.

- **`selfServiceSignup`** gives a user a global role carrying only
  `create:tenants`, once their email is verified. It never carries read,
  delete or organization-admin rights.
- **A creator gets a role that fits.** Through `initMultiTenant` the creator
  of a tenant was being made a member of its organization with **no role at
  all**; that is fixed. A creator who already holds the operator scopes gets
  Tenant Admin. Everyone else gets a new, narrower **Tenant Owner** role:
  every management scope except creating and deleting tenants, organization
  administration, rollouts and tenant operations — so the role never grants
  more than the person had. **This changes what a non-operator creator
  receives**; existing creators keep the role they have.
- **`tenantCreationLimits`** caps how many tenants a non-operator may own,
  and by default stops someone creating another while one is still being
  provisioned. An operator can raise or lift the limit for one user through
  `app_metadata.tenant_limit`. `GET /tenants/creation-limit` tells a user
  where they stand, and the admin UI shows "2 of 3 tenants used" next to
  Create.
- **`tenantDefaults`** sets a new tenant's own settings — MFA, attack
  protection, session lifetimes, flags — at creation. They are copied once:
  changing the defaults later does not reach existing tenants, and the tenant
  can change every value.

For tenants with their own database, those defaults now reach the tenant's
own row, and a new tenant's default application is created in its own
database rather than the control plane's.

## MFA can remember a device

Users can tick "Remember this device for N days" on the TOTP and SMS
challenge screens, and later logins from that browser skip the challenge for
that period. It is offered only when everything requiring MFA for the login
allows it: the tenant, through the new `mfa.allow_remember_browser` setting —
**off by default, so nothing changes until you turn it on** — and any
post-login action, through
`api.multifactor.enable(provider, { allowRememberBrowser: true })`.
`mfa.remember_browser_lifetime_in_days` sets the period, 30 days by default;
lowering it shortens devices already remembered.

A remembered device satisfies the MFA requirement but is not MFA: those
logins get no `amr` claim, and the session is not marked as having completed
MFA. It never skips enrollment.
`POST /api/v2/users/{id}/multifactor/actions/invalidate-remember-browser`
makes every remembered browser for a user complete MFA again.

## Self-Service SSO: the groundwork

Self-Service SSO lets a customer's own administrator connect their identity
provider to your tenant through a link you send them. Three pieces landed;
the setup screens the link opens come in a later release, so **the ticket URL
does not open a page yet.**

- **The management API**, Auth0-compatible, under
  `/api/v2/self-service-profiles`: profiles, their custom text, and the SSO
  tickets issued from them. Fields Auth0 defines that AuthHero does not
  implement yet are rejected with a 400 naming the field, rather than
  accepted and ignored.
- **Storage** for profiles and tickets on kysely and drizzle. A ticket is
  stored only as a hash.
- **A guard on account linking.** An identity provider configured by an
  outside administrator must not be able to claim your existing users by
  asserting their email addresses. For a self-service connection, an email is
  trusted only inside the domains verified for it: outside them, users are
  stored as unverified and excluded from automatic linking. Ordinary
  connections are unchanged.

## Database connections as separate user stores

Every database connection stores its users under the same provider, so a
lookup by email could find a user belonging to a different database
connection of the same tenant. That made a second database connection
unusable as a separate set of users — which Custom Token Exchange needs, to
keep exchanged users apart from password users.

Password login, password reset, the `/dbconnections` endpoints, invitations
and the ticket flow now look users up within the connection they target. A
tenant with a single database connection sees no difference. In the same
spirit, a token exchange profile now resolves only users in its own
connection: a subject that happened to match the ID of a password user used
to receive tokens for that user, and is now refused. The admin UI's profile
form warns when the chosen connection is also used for login and recommends a
dedicated one.

## Upload branding files

The admin UI's branding page has upload buttons for the logo, favicon, font
and background image, where you previously had to host the file yourself and
paste a URL. Behind it is a new optional storage adapter, with an R2
implementation in the Cloudflare adapter, and
`POST /api/v2/branding/uploads/{kind}`. Uploads are checked for type, size
and content; SVG files are validated and always served with a restrictive
content security policy.

## Migrations

- **Sessions and refresh tokens** gain a `session_transfer` column, and
  connections a `self_service` column. Run these before deploying. A custom
  adapter must also implement the new `refreshTokens.isFamilyActive`.
- **Self-Service SSO** adds two tables; they only add, so they are safe to
  run ahead of the code.
- **Drizzle adds unique indexes** on a resource server's identifier and an
  organization's name, per tenant — kysely always had them. **The migration
  fails if a tenant already holds duplicates.** Check for and resolve
  duplicates before you deploy. Afterwards, renaming an organization or
  re-pointing an API onto a taken value answers 409 instead of a raw database
  error.

## Also

- **Email** — a tenant's `sender_email` and `sender_name` were never used
  when sending mail. They are now the fallback when neither the template nor
  the email provider names a sender, and the admin UI edits them under
  Settings. The last-resort address is also valid now; it used to be built
  from the whole issuer URL.
- **Statistics on Cloudflare** — once Analytics Engine starts sampling a busy
  dataset, each stored row stands for several events, and the daily stats and
  analytics endpoints were counting rows. They now weight by the sample
  interval. Distinct-user counts cannot be corrected that way and are
  documented as a lower bound.
- **Management API** — creating a user through the management API no longer
  runs signup validation when the caller's token happens to name an
  application in the target tenant; it could fail with "User account does not
  exist" on a connection with signups disabled.
- **MCP clients** — a login by a client identified by a metadata URL could
  resume in the wrong tenant when several tenants knew the same client. The
  tenant is now taken from the login session.
