# Week 44 · 26 October – 1 November 2026

The biggest week since this changelog began. **Management API error bodies
changed** to match Auth0's, which breaks any client that matches on error
message text. The device authorization grant is implemented, so a TV or a
command-line tool can sign a user in through a browser on another device.
Tenant configuration inheritance, whose schema landed last week, is now a
complete system: a parent tenant publishes connections, actions and settings,
child tenants receive them through tracked sync operations and staged
rollouts, and a tenant can be verified against its parents or detached from
them. Actions gained four lifecycle triggers and a single Triggers page, team
changes on a sharded deployment can be registered as requests, and
`@authhero/cloudflare-adapter` moves to 4.0 with one breaking change.
Everything also has a new look.

## Management API errors match Auth0

**If your code matches on an error message, it will break. Match on
`errorCode` instead.** The management API's error bodies were AuthHero's own;
they are now Auth0's, captured from a live Auth0 tenant, so the Auth0 SDKs
and the Terraform provider see the errors they were written against.

- **Not found and conflict** use Auth0's `message` and `errorCode` — for
  example `404 {"message":"The user does not exist.","errorCode":"inexistent_user"}`,
  where the message used to be "User not found". Where Auth0 sends no
  `errorCode`, AuthHero adds one (`inexistent_role`,
  `inexistent_organization` and others); every addition is listed under
  "AuthHero extensions" in the error-codes reference.
- **Validation errors say what failed**: `invalid_body`,
  `invalid_query_string` or `invalid_uri`, in Auth0's message format, and
  `invalid_json` for a malformed body.
- **Deleting something that does not exist answers 204** for users,
  applications, connections, resource servers and client grants, as in Auth0.
  These used to answer 404.
- **An invalid token is a 401**, not a 403. Missing authentication is
  `401 Missing authentication`, and a token without the needed scope is
  `403 insufficient_scope`.
- A control-plane token naming a tenant that does not exist gets
  `404 inexistent_tenant` instead of a misleading "resource not found".

## Sign in from a TV or a terminal

The OAuth device authorization grant is implemented. A device that has no
browser, or no keyboard worth using, calls `POST /oauth/device/code`, shows
the user a short code and a URL, and polls `/oauth/token`. The user opens the
URL on a phone or laptop, enters the code, signs in — with MFA and post-login
hooks exactly as for any other login — and approves or denies the request.

- Enable it per application with the **Device Code** grant type in the admin
  UI. Discovery metadata advertises the endpoint when storage for it is
  configured.
- Pass `include_qr_code=true` and the response includes an SVG QR code for
  the complete verification URL, for the device to display.
- Device codes are stored hashed and can be redeemed once. Polling too fast
  is answered with a growing back-off, and attempts to guess a user code are
  limited.
- The code-entry and approval screens exist on `/u2` only.

**Apply the kysely or drizzle migrations before enabling the grant.** The
DynamoDB adapter needs no migration.

## Tenants inherit configuration from a parent

Until now a child tenant could fall back to the control plane's connections
and settings at read time, and that was the whole model. This week replaces
it with one you can reason about and roll out:

- **A parent publishes, per row.** Connections, actions, hooks, resource
  servers, branding, prompt settings and email providers carry a `scope`
  (`local`, `shared`, or `platform` for rows a child runs but never sees), an
  `override` rule for what a child may change, and `enforce`. A tenant names
  its `parent_tenant_id`; only a control-plane credential can set it.
- **A tenant chooses how it receives.** `config_sync` is `inherit-on-read`
  (the default — today's behaviour) or `synced`, where the parent chain is
  materialised into the tenant's own database and the tenant reads only that.
  Synced copies have deterministic IDs and a content hash, so an up-to-date
  sync is a no-op.
- **A sync is a tracked operation.**
  `POST /tenants/{id}/operations` with `kind: "sync-defaults"` syncs one
  tenant, with step events and history; `dry_run` returns the diff without
  writing, and `prune` removes copies the parent has stopped sharing. A
  tenant's own connection, API or action with the same key wins over a synced
  copy rather than colliding with it.
- **Fleets roll out in waves.** A rollout syncs every synced tenant below a
  root: a canary first, then growing percentages, parents before children,
  pausing itself if the failure rate crosses a threshold. Management API
  writes to published rows request a rollout automatically, and a drift check
  compares each tenant's applied hash with what its chain now resolves to.
  Routes live under `/api/v2/rollouts`, with new `read:rollouts`,
  `create:rollouts` and `update:rollouts` scopes.
- **Platform rows are invisible to the tenant.** A `platform`-scoped copy is
  left out of the tenant's management API lists, answers 404, cannot be
  referenced, and is omitted from tenant exports — while still running.
  `override` and `enforce` are enforced on synced copies.
- **You can check, and you can leave.**
  `GET /api/v2/tenants/{id}/config-sync` reports a tenant's parent, mode,
  hashes and what it inherits from whom; `…/config-sync/verify` compares it
  against its parents on demand, read-only. A `detach` operation makes a
  synced tenant independent: its copies become its own rows, and it neither
  inherits nor is synced again.

To make copying safe, action and hook-code secrets are now encrypted at rest
by the encrypted data adapter, like application and connection secrets
already were; existing plaintext rows keep working and are encrypted the next
time they are written. A sync refuses to write if the receiving tenant cannot
decrypt a key the payload uses.

The admin UI covers all of it: publishing controls on each row, an
"inherited from" notice that locks what a parent does not allow changing, a
sync status card with Verify, an Operations page that shows what a sync
changed, and a Rollouts page. On Workers for Platforms, sync, detach and
shadow mode all reach tenants that have their own database.

**Migrations to apply:** tenants gain `config_sync`, `config_sync_hash` and
`config_synced_at`, and the rollouts table gains two columns. Nothing changes
for a tenant until you set `config_sync: "synced"`; the new runbook in the
docs walks through migrating one — dry run, sync with inheritance still on,
verify, flip, watch, and how to roll back. A mode change reaches every worker
within about ten seconds, though a deployment that caches the client bundle
can take up to fifteen minutes to follow it at login.

## Actions: lifecycle triggers, one Triggers page, drafts from a prompt

- **User update and deletion.** Actions can bind to `pre-user-update`,
  `post-user-update`, `pre-user-deletion` and `post-user-deletion` —
  AuthHero extensions. A pre action can refuse the write with
  `api.access.deny(reason)` and fails closed if it errors. A post action is
  delivered through the outbox, at least once, so deduplicate on
  `event.idempotency_key`. A denied deletion — through SCIM or self-service —
  leaves the account and its sessions intact.
- **Signup validation.** Actions can bind to the registration-username
  validation trigger and run synchronously with the email, connection and
  application; a denial or a failure blocks the signup.
- **A five-second deadline.** The host now stops waiting for an action after
  five seconds and discards anything it does afterwards.
- **One Triggers page.** The admin UI's separate Hooks and Triggers screens
  are one page listing every binding — action, webhook, form, template or
  page — with one way to add and edit them. The Actions page remains the code
  library. Old hook links still work.
- **Generate a draft from a prompt.** With an optional generator adapter
  configured — a Cloudflare AI Gateway implementation ships in the Cloudflare
  adapter — the Actions editor can draft an action from a description. The
  generator is given the typed API of the trigger it is writing for, and the
  draft is verified statically before it can be saved. With a generator
  configured, that verification is also enforced on the server for action
  writes and deployments.

## Team changes as requests

On a sharded deployment, a tenant's team is an organization on the control
plane, which the tenant's own worker cannot change directly. With
`tenantMembers.requests` set, the write routes of `/api/v2/tenant-members` —
invite, add, remove, change roles — store the change as a request on the
tenant and answer `202`. The control plane picks it up, checks that the
requester is still an administrator of that tenant, carries it out and writes
the outcome back. The admin UI's Team page shows requested changes as
waiting, done or failed, with the reason. Without the option, the routes act
immediately as before.

**The tenant database migration must be applied before you deploy code that
writes requests.** It adds a `tenant_member_requests` table on kysely and
drizzle.

## `@authhero/cloudflare-adapter` 4.0

**One breaking change.** `createWfpForwardMiddleware`'s `localPaths` now adds
to the default list of paths served locally instead of replacing it, so a
default added in a later release is not silently dropped by a caller passing
its own list. The consequence: `localPaths: []` no longer turns the default
off. Pass `includeDefaultLocalPaths: false` for that; the middleware warns if
it sees the old form.

The change came out of a fix. With `tenantDispatch` set, the control-plane
routes AuthHero mounts itself — team members, operations, rollouts — were
being forwarded to the tenant's worker, which then had to call back to the
control plane. Where that call never arrived, every request from the admin
UI's Team page answered 404 "The member does not exist". Those routes are now
served by the control plane, and a 404 from it is told apart from a missing
team.

## A new look

The marketing site, the admin UI and this documentation site share a new
design: ink and saffron, Familjen Grotesk and JetBrains Mono, and a saffron
plus as the mark. The admin UI's dashboard gained bar charts and recent
activity, and a user's page a header with avatar, verified badge and ID.
Exact prices are off the website until AuthHero Cloud launches.

## Also

- **Audit log** — a user deleting their own account from the account page
  produced a log entry that did not say who had done it. Changes made under a
  browser session now record the caller in `details.request.auth` with
  `strategy: "session"`.
- **Prompt partials** — the insertion points are laid out as Auth0 lays them
  out: footer partials sit below the submit button around the bottom links,
  and the secondary-action partials wrap the social buttons. Adding a partial
  no longer moves the sign-up link above the submit button. The admin editor
  previews every insertion point as a labelled placeholder.
- **Admin UI** — a JSON button on list pages, table tabs and raw views copies
  or downloads the rows shown, or the ones selected.
- **Docs** — a reference for every parameter `/authorize` accepts, including
  choosing the language with `ui_locales` and how the classic and `/u2`
  logins resolve it differently.
